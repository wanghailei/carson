# Test Quality Infrastructure Plan

2025-03-25. Context: one person, 10 concurrent agents, enterprise Ruby on Rails + Python systems. Any code generated by agents must meet the quality standard defined in `~/AI/core/TESTING.md`.

## What exists today

**Present:**
- Minitest with real-git integration tests (no mocking)
- CI runs tests + 5-job pipeline (governance, lint, test, smoke-canary, smoke-full)
- Pre-commit hooks (9 guards) — secrets, branch, structure, naming
- Lint configs managed by Carson (`~/AI/core/CODING/LINT/` → `.github/linters/`)
- Delivery gates (PR freshness, CI status, review decision)
- 773-line smoke test script exercising end-to-end workflows

**Missing:**
- No coverage measurement (SimpleCov, pytest-cov, etc.)
- No mutation testing
- No test-pass gate in `carson deliver` before push
- No RuboCop enforcement in CI (only syntax + indentation)
- No test result publishing (no JUnit XML, no coverage reports)
- No slow-test detection

## Infrastructure components

### 1. Coverage measurement (per-language)

| Language | Tool | Output | Threshold |
|----------|------|--------|-----------|
| Ruby | SimpleCov | `coverage/` directory, JSON + HTML | Defined by TESTING.md |
| Python | pytest-cov | `.coverage` + XML | Defined by TESTING.md |
| JavaScript | c8 | `coverage/` directory | Defined by TESTING.md |
| Rust | cargo-tarpaulin | XML | Defined by TESTING.md |

Each project's test helper wires coverage at load time. Coverage data is the raw material — thresholds come from TESTING.md.

### 2. Coverage reporting (universal)

A small script (Ruby, lives in `~/AI/enforce/` or Carson-managed) that:
- Reads coverage output from any supported tool
- Compares against TESTING.md thresholds
- Outputs a pass/fail verdict with uncovered file list
- Exit code 0 (pass) or 1 (fail)

Agents consume this verdict. CI publishes it. Same script, every language, every project.

### 3. Local quality gate in Carson deliver

Before push, `carson deliver` runs:
1. **Tests pass** — run the project's test command, block on failure
2. **Coverage met** — run coverage reporter, block if below threshold
3. **Lint clean** — run the project's linter, block on violations

This is the enforcement point. No agent can deliver code that fails these checks. Same authority as the existing "cannot deliver from main" guard.

Opt-out: `carson deliver --skip-quality` with a mandatory reason logged. The escape hatch exists but leaves a trail.

### 4. RuboCop / linter enforcement in CI

Add a CI job that runs the actual linter (not just syntax check):
- Ruby: `rubocop -c .github/linters/rubocop.yml`
- Python: `ruff check`
- JavaScript: `biome check`

This catches what pre-commit hooks miss (agents can bypass hooks with `--no-verify` in emergencies).

### 5. Mutation testing (deferred — infrastructure-ready)

Wire the infrastructure now, enforce later:
- Ruby: `mutant` gem as dev dependency
- Python: `mutmut`
- A runner script in `~/AI/enforce/` that executes mutation testing and reports survival rate

Mutation testing is expensive (slow). Run it on-demand or nightly in CI, not on every delivery. The infrastructure is ready; TESTING.md decides when it's mandatory.

### 6. Test result publishing in CI

Add JUnit XML output so CI can surface individual test failures:
- Ruby: `minitest-reporters` gem → JUnit format
- Python: `pytest --junitxml=`
- GitHub Actions: upload as artefact, surface in PR checks

## Design decisions

1. **Carson deliver is the enforcement point** — not CI alone. CI catches what slips through, but the local gate is the primary defence. Agents hit it before code leaves the machine.

2. **Thresholds live in TESTING.md, not in tooling.** The infrastructure measures and reports. The standard defines what's acceptable. Clean separation.

3. **Language is just configuration.** The reporter script accepts coverage data from any tool. Adding Rust or Go means adding one tool config, not redesigning the system.

4. **Mutation testing is phase 4, not phase 1.** It's the deepest quality signal but also the most expensive. Get coverage measurement working first — it solves 80% of the "do we know?" problem.

## Layers

The full quality assurance system has three layers:

| Layer | Mechanism | What it does |
|-------|-----------|--------------|
| **Standard** | `~/AI/core/TESTING.md` | Defines what "good enough" means — universally, language-agnostic |
| **Infrastructure** | Per-project tooling (SimpleCov, pytest-cov, etc.) + Carson deliver gate | Mechanical measurement and enforcement |
| **Review** | Agent or skill (future) | Independent judgement — "is this *well* tested?" — the SDET eye |

The standard is done. The infrastructure is this plan. The review layer comes after the infrastructure produces data for it to consume.
